① ESP32 主板 ↔ AIPC：WebSocket

port 81，ws://<esp32-ip>:81/api/v1/stream。取代原本規劃、但從未實作的 USB Serial 通道（麥克風/相機資料量太大不適合 115200 baud 序列，且 touch/say/expr 從沒寫過 serial 版本，直接定案成 WebSocket）。訊息格式定義在 ai-pc-agent/protocol.py；韌體實作在 esp32-bringup/include/companion_app.h（Stage 13，還沒有實機驗證過）。

ESP32 → AIPC：手勢事件

規劃中
{"t": "touch", "kind": "squeeze", "strength": 0.8, "dur_ms": 1200}
  • kind：squeeze 捏、pat 拍、shake 搖、lift 拿起、putdown 放下、double_tap 壓 FSR1 兩下（觸發 §⑥ 作業拍照流程）
  • 「捏／搖／雙擊」都在 ESP32 本地判斷，只送離散事件，不串流原始數值
  • double_tap 閾值/防抖是 [CANDIDATE]（見 companion_app.h 的 FSR1_PRESS_THRESHOLD），還沒拿真實按壓校準過

ESP32 → AIPC：麥克風

規劃中
<binary frame>  // INMP441，mono int16 little-endian PCM，16kHz

AIPC 收到後轉成 float32、轉送本機 STT 服務（見 §⑦）。

AIPC → ESP32：說話 / 換表情 / 蜂鳴器

規劃中
{"t": "say", "expr": "thinking", "text": "你已經卡這個 bug 40 分鐘了…"}
{"t": "expr", "expr": "sleepy"}                 // 只換表情、不說話
{"t": "buzz", "pattern": "confirm"}             // 蜂鳴器音效回饋
  • expr：neutral happy joy love sad sleepy surprised thinking worried（見 protocol.py 的 EXPRESSIONS）
  • text：最多 40 字（1.8" LCD，實測後再調）
  • LCD 韌體（lcd_faces.h）新增畫了 neutral/thinking/worried 三種臉，沒有實機驗證過視覺效果
  • pattern 目前只認得 confirm，其他字串安全 fallback 成一聲短嗶，不會讓韌體卡住或斷線

③ 截圖觀察：AIPC → MI300

AIPC 送截圖，VLM 回一句描述，AIPC 再寫進本機記憶。呼叫端：ai-pc-agent/mi300_client.py，格式：observation_models.py。

④ 對話回覆：AIPC → MI300

使用者開口，或主動發話規則觸發時呼叫。組 prompt：ai-pc-agent/prompt.py；相關記憶檢索：ai-pc-agent/memory/retrieve.py（hybrid vector+BM25，已實作，見 memory.md）。

POST

/v1/chat/completions

已上線

刻意沿用 OpenAI 相容格式，不是 /v1/replies 之類的資源式命名——這樣可以直接用任何 OpenAI SDK/工具測試，且跟 Ollama 生態相容。

送（OpenAI 相容格式）
{
  "messages": [
    {"role": "system", "content":
      "你是桌上的毛茸茸桌寵…只回 JSON：
       {\"expr\": ..., \"text\": 不超過 40 字}"},
    {"role": "user", "content":
      "【使用者檔案】在做 ESP32 桌寵專案
       【現在】app：code / 活動：main.py 除錯
       【最近狀態】[09:20–10:00，40 分鐘] 在 main.py 遇到 KeyError
       【相關記憶】…
       【觸覺】剛被用力捏了一下
       【使用者說】這個到底怎麼修"}
  ],
  "response_format": {"type": "json_object"}
}
收（取 choices[0].message.content）
{"expr": "worried",
 "text": "KeyError 通常是 key 拼錯，要不要先印出 dict 看看？"}
  • 回傳的 JSON 直接轉成 ① 的 {"t": "say", ...} 送給 ESP32，同時存回記憶（source="reply"）
  • 【使用者說】為空代表主動發話（例如同一件事做太久）
  • MI300 連不上時用本機 fallback 句子（main.py:_reply），不能讓 demo 卡住

⑥ 作業拍照分析：AIPC → MI300

壓 FSR1 兩下觸發（① 的 double_tap）→ AIPC 開相機預覽、倒數 5-4-3-2-1（同時收 STT 逐字稿）→ 倒數結束打一次 ② 的 snapshot → 呼叫這支 API。流程細節見計畫第 8 節。

POST

/v1/homework-analyses

已上線
送
{
  "image_b64": "<倒數結束擷取的 JPEG>",
  "transcript": "這題我算了好久都算錯..."
}
收
{
  "analysis": "題目：... 使用者已寫：...",
  "reassurance": {"expr": "happy",
    "text": "算對了，很棒！"},
  "chatgpt_prompt": "以下是我卡住的題目..."
}
  • 跟 ③ 的差別：這裡要求盡量逐字轉錄（含算式/符號），不是一句話 caption，也不解題
  • MI300 不落地任何資料（符合「mi300 只暫存、用完即刪」的要求）
  • AIPC 收到後：① reassurance 走跟 ④ 一樣的下行 say；② 寫 memory.add_or_extend("homework", analysis, ...)；③ 把 chatgpt_prompt 交給 ai-pc-agent/chatgpt_bridge.py（Playwright，接上使用者已開好的 ChatGPT 分頁）
Playwright 這段依賴使用者的 Chrome 有開 --remote-debugging-port、且 ChatGPT 分頁在預期狀態；ChatGPT 網頁改版會讓選取器失效，這是 API 設計解決不了的外部依賴，上線前要先用 §⑧ 的 /debug/homework 對著真的分頁測過一次。
